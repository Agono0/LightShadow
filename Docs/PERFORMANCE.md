## Targets (engineering pass, P2)

### Frame rate policy (decision D8 — the honest statement)

- **Windows:** `Application.targetFrameRate = 120`, `QualitySettings.vSyncCount = 0` at boot.
  120 FPS means an **8.3 ms frame budget** (GPU + CPU + engine overhead). This is an
  *uncapped* target, not a promise: it is achievable on High/Ultra hardware on this content
  (one interior school, one consequential realtime light), and the tiers below are the
  mechanism that keeps a frame inside 8.3 ms when the hardware cannot. The player's VSync
  toggle in the settings card still wins after boot.
- **Android:** request the display refresh (`Screen.currentResolution.refreshRateRatio`),
  clamped 60–120, fall back to 60 when the panel does not report one; vSync off (Android
  frame pacing owns the cadence). 120 Hz-capable devices get the 120 Hz path on High tier;
  mid-range devices settle at a **stable 60** on Medium/Low — a locked 60 is worth more
  than a fluctuating 120.

### Quality tiers (PerformanceManager, runtime)

| Tier | Auto-detect | Pipeline asset | Render scale | Shadow dist | MSAA | Soft shadows | SSAO | Dynamic res | Target |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Low | Android GPU mem ≤ 2 GB | Mobile (no SSAO renderer) | 0.65 | 0 | off | off | no | off | stable 60 |
| Medium | Android GPU mem ≤ 4 GB | Mobile (no SSAO renderer) | 0.75 | 20 | off | off | no | off | 60 (120 Hz panels may hold 90–120) |
| High | Android > 4 GB / Windows default | PC (SSAO renderer) | 0.90 | 40 | 2x | on | yes | on, min 60 % | 120 (8.3 ms) |
| Ultra | Windows GPU mem ≥ 8 GB | PC (SSAO renderer) | 1.00 | 60 | 2x | on | yes | on, min 70 % | 120 (8.3 ms) |

Notes, honestly stated:

- **SSAO** is a renderer feature. Low/Medium run the Mobile renderer without SSAO and
  High/Ultra the PC renderer with it — the asset swap encodes the on/off decision. Toggling
  the feature itself at runtime is not reliably scriptable headlessly, so it is not toggled
  at runtime; tiers swap whole assets instead.
- **Shadow distance 0 on Low** is a global culling distance in URP — it disables *all*
  realtime shadows on that tier, including the flashlight's. The flashlight's own realtime
  shadow *flag* is never touched at any tier (PerformanceManager never modifies Light
  components); the distance culling is the documented cost of the Low tier.
- **Shadow distance fade** was requested per tier; URP 17.4 no longer exposes that field on
  the render pipeline asset (no public setter, no such serialized field in 17.4 assets), so
  it stays at asset defaults on every tier.
- **Dynamic resolution** uses URP 17.4's core `DynamicResolutionHandler` (per-tier min/max
  pushed at runtime, guarded) plus the stable `Camera.allowDynamicResolution` flag on game
  cameras (High/Ultra only). In URP 17.4 these settings no longer live on the RP asset, so
  there is nothing asset-side to variant.
- **Adaptive Performance package (D16) was deliberately skipped** — provider setup cannot be
  verified headlessly and it adds package risk. The runtime tier system + refresh-rate
  targeting above is the agreed mitigation; the manual override (`ls_qualityTier` in
  PlayerPrefs, -1 = auto, values 0-3) is exposed for a settings-card entry via
  `PerformanceManager.SetTierOverride(int)`.
- Asset variants `Assets/Settings/RP_Low|Medium|High|Ultra.asset` are generated by
  `SceneBuilderSystems.ConfigureQualityForBuild()` (editor tool) so a build can bind real
  per-tier assets into QualitySettings later. Runtime tuning does not depend on them.

## Methodology (how the Lead measures)

1. **Batch numbers:** after each P2 integration run, grep the batch logs —
   `grep -E "RESULT:|error CS|Exception" Logs/*.log`. ValidateBatch PASS is the gate for
   every code drop; BuildWindowsBatch / BuildAndroidBatch sizes come from the output
   folder (`ls -la Builds/Windows/LightShadow.exe`, APK file size).
2. **Frame budget math:** 120 FPS = 1000 ms / 120 = **8.3 ms/frame**; 60 FPS = 16.6 ms.
   On-device check: vSync off, on-screen FPS counter or Android GPU profiler. A tier
   "passes" when the *1 % worst* frame stays under budget across a full corridor sweep plus
   one chase — averages hide the stutter that matters.
3. **Build sizes:** compare APK/EXE sizes against the baseline table; Cinemachine adds
   runtime code only (no content), so the expected delta is small (< 1 MB).
4. **Device tiering:** PerformanceManager prints one boot summary line
   (`[LightShadow] Performance: tier=… targetFps=… renderScale=… shadowDistance=… device=… gpuMemoryMB=…`)
   — capture it per test device alongside the achieved frame rate.
5. **CPU profiling:** Unity Profiler on a development build; record PlayerLoop time for
   02_School at spawn, mid-run and dawn chase. Rows below stay **MEASURED BY LEAD** until
   then.

### GI bake note (D11, honest)

`BakeLightingBatch` was exercised twice: with `-nographics` it correctly refuses (exit 1);
with a graphics device the async bake started but the ProgressiveCPU lightmapper stalled
in batchmode on this machine (near-idle process for 15+ minutes) and was terminated. What
ships regardless: light-probe grids per wing, 3 baked-ready reflection probes, static
batching/GI-contribution flags, scene fog. The bake remains a documented follow-up runnable
from the editor UI (LightShadow ▸ Art ▸ 3) where progress is visible and cancellable.
